# 咨询层：真实模型验证记录（2026-10-27）

目的：在隔离的本地库副本上，用真实模型验证“咨询层”能否把已核验的证据写成咨询式报告，并记录被程序校验拦下的情况。

## 环境与口径

- 数据：交接包线上快照的**独立恢复副本**（库 `cyshuhe_dev_llm`，迁移 0023→0024）。没有触碰另一份恢复库和线上系统。
- 模型：`deepseek-flash`（系统默认），密钥只经当前进程环境变量输入，未写入任何文件。
- 场景：新加坡；中国车企联网车辆数据每日回传；业务事实为设定的演示情景，**不是真实客户信息**。
- 任务由 `run_pipeline` 真实执行（检索、选证、核验、补证、编制、咨询层），遇到分析中追问时按场景设定回答。
- 这是**少量样本的工程验证**，不是准确率评测；没有人工法律复核，所有输出都是机器草稿。

## 发现与处理

1. **首个真实缺陷（已修）**：模型正常作答、明确说明现有法源不适用于该场景，被流水线当成技术失败，导致整份报告 `analysis_failed` 且禁止导出。现改为“法源缺口”，其余维度照常交付；模型报错、选了却没通过核验、补证未完成仍按技术失败，既有相关测试全部保持通过。
2. **版式类问题只修版式（已修）**：信息不足时多给的评分被忽略；信息不足漏写理由时用“需补充事项”补上；去掉“结论：”前缀；建议误挂在信息不足的差距上时只去掉这条关联。**实质规则未放宽**：判“达到/未达到”仍必须引用业务事实；非信息不足缺理由仍拒绝；数字、角标、照抄、风险等级校验不变。
3. **建议重复（已修）**：不同维度各提一条“重做告知同意”，路线图重复。试过按文字相似度合并，实测同一件事的两种写法相似度仅约 0.2，无法区分，放弃；改为（a）类别相同且解决的差距集合相同的结构性合并，（b）由结论页模型指出实质重复的分组，程序校验分组（编号存在、同类别、不重叠）后再合并。合并后每个差距仍被覆盖。
4. **程序校验起了作用**：第 4 次 D6 的结论里出现证据和业务事实都没有的数字，被拦下、没有进入报告。该维度显示“咨询意见暂时没有生成”，证据版内容保留。
5. **D2 没有产出建议**：第 4 次里 D2 只有 1 个差距且以信息不足为主，没有可整改的差距，所以没有建议，这是规则的预期结果。

## 质量观察（定性，仅此一次样本）

- 结论页能直接回答“能不能做、卡在哪、先做什么”，路线图每条有类别、责任角色、时限、完成标准，并挂回具体差距。
- 建议偏法务/流程类仍然偏多；车端、数据架构类的工程化建议在提示词里有要求，但实测占比不高。需要在下一轮用 EDPB 车联网指南等入库文本加强（该指南尚未入库，不能被引用）。
- 个别结论写法偏长，已在提示词限制长度，未做统计。

## 未验证 / 局限

- 只完整跑了 1 个场景的 4 次，没有统计通过率。另一个对照场景（措施较完整）只跑到模型提出分析中追问就停了（当时的运行脚本还不会回答追问），后来给脚本加了自动回答追问，但没有再重跑该对照场景，所以“措施较完整时报告是否合理”没有验证。
- 没有人工评分，没有对照标杆样稿，没有测量不同运行之间的稳定性。
- 咨询层增加的耗时和用量：本次一次完整任务约 4–5 分钟、约 43–46 万 token（含证据层；咨询层单独约 7–9 万）。未做并发测试。
- 中国出境规则、EDPB 车联网指南未入库，报告里的“数据识别与路径判定”“工程化建议四类”尚未实现。
